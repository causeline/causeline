How a click becomes a trace

Six steps, from the button your user presses to the insight that names the slow call. Standard headers, Micrometer and OpenTelemetry, nothing proprietary.

In the browser

The click gets a name

@causeline/react wraps fetch and XHR. Wrap a handler in trace() and the click becomes the root of a trace, with every request and state update inside it.

Checkout.tsx
const onCheckout = () =>
  trace('Checkout', async () => {
    const res = await fetch('/api/orders', { method: 'POST', body });
    setStatus(res.ok ? 'paid' : 'failed');
  });
On the wire

The header carries it

Each request to your own API gets a W3C traceparent header: the trace ID, the span that sent it, and a sampled flag. Calls to other origins are left alone.

POST /api/orders
traceparent: 00-8969ad7e690b50a8721f9fd8e0e5c925-00f067aa0ba902b7-01
#              trace id                         parent span      sampled
In Spring Boot

Spring Boot joins in

The starter reads the header and builds on Micrometer Observation. Controllers, @Observed services, repositories, transactions, JDBC and R2DBC queries, outbound calls and messages become spans in the same trace.

  • REQUESTPOST /api/orders925 ms
  • CONTROLLEROrderController.createOrder915 ms
  • TRANSACTIONOrderService.createOrder907 ms
  • DATABASEinsert into orders (item, quantity) values ('book', 1)3 ms
  • SERVICEPaymentClient.charge857 ms
  • HTTP CLIENTPOST /fake-payment/charge844 ms
Inside your app

It lands at /causeline

Browser spans upload to /causeline/api/spans; server spans go through a bounded queue that never blocks a request. Both land in an in-memory store inside your app, lined up by the span tree, not by clocks.

Application log
INFO  CauselineWebConfiguration : Causeline UI: http://localhost:8080/causeline/?token=…

Open the link and the whole action is there. The store keeps the latest 1,000 traces, within 64 MB.

Insights

Rules read the tree

Self time is a span’s duration minus the time its children ran. The rules use it to name the bottleneck, then look for repeated queries, long transactions and exceptions.

BottleneckPOST /fake-payment/charge · 844 ms · 88% of the checkout.

Long transactionOrderService.createOrder lasted 907 ms, 844 ms of it waiting for the payment call. It holds a database connection the whole time.

After the fix

Replay, compare, keep

Replay the captured request to local, dev or QA, then compare the two runs span by span. When it’s right, copy it as a test so it stays right.

CreateOrderTest.java
causeline.trace("POST /api/orders")
    .hasNoFailedSpans()
    .hasQueryCountAtMost(2)
    .hasNoRepeatedQueries();
